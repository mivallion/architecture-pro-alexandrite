# Выбор и настройка мониторинга в системе

## Мотивация

На данный момент наблюдаемость системы ограничена Яндекс Метрикой. Она показывает пользовательскую активность интернет-магазина, но не позволяет наблюдать B2B API, CRM, MES, инфраструктуру и сквозной процесс обработки заказа. Поэтому компания не может оценить доступную производительность системы и безопасный объём новых B2B-заказов. Решения о масштабировании, допустимом объёме B2B-трафика и архитектурных изменениях принимаются без данных о фактической нагрузке. Это увеличивает риск деградации системы, недовольства и ухода клиентов и, как следствие, финансовых потерь.

При возникновении проблемы поиск её первопричины требует значительного времени разработчиков и инженеров, а сама проблема зачастую обнаруживается только после обращения пользователей. Мониторинг позволит сократить Mean Time to Detect (MTTD) и Mean Time to Repair (MTTR): обнаруживать деградацию раньше пользователей, находить заказы, которые слишком долго остаются в одном статусе, предупреждать команду о перегрузке компонентов и быстрее устанавливать причины инцидентов.

## Выбор подхода к мониторингу

- **RED** — для Shop API, CRM API и MES API. Для каждого API необходимо отслеживать Rate, Errors и Duration: интенсивность запросов, долю ошибок и время ответа.
- **USE** — для инфраструктуры приложений и БД. Необходимо отслеживать Utilization, Saturation и Errors для CPU, RAM, дисков и пулов соединений с БД.
- **Four Golden Signals** — для сквозного процесса обработки заказов. Traffic показывает поток новых заказов, Latency — время обработки, Errors — неуспешные операции и зависшие заказы, Saturation — накопление задач в очередях и исчерпание ресурсов.

Подходы дополняют друг друга: RED показывает состояние сервисов, USE помогает найти ограниченный ресурс, а Four Golden Signals связывает технические показатели с пользовательским сценарием обработки заказа.

## Выбранные метрики

### Общие правила для labels

Для технических метрик используются общие labels `environment`, `service` и `instance`. Для HTTP-метрик в `route` записывается шаблон маршрута, например `/orders/{id}`, а не фактический URL. Значения `order_id`, `user_id`, имя файла и текст SQL-запроса в labels не добавляются: большое число уникальных значений приведёт к высокой cardinality и перегрузке Prometheus.

### API

| Метрика | Где собирается | Зачем нужна | Дополнительные labels |
|---|---|---|---|
| Количество HTTP-запросов и RPS (`http_requests_total`) | Shop API, CRM API, MES API | Показывает текущую нагрузку, её распределение между API и изменение после подключения B2B. RPS рассчитывается как скорость роста счётчика | `route`, `method`, `status_code`, `client_type`; для контролируемого списка B2B-клиентов MES API — `partner_id` |
| Время ответа (`http_request_duration_seconds`) | Shop API, CRM API, MES API | Позволяет отслеживать p50, p95 и p99 latency, находить деградацию API и медленные маршруты | `route`, `method`, `status_class` |
| Активные запросы (`http_active_requests`) | Shop API, CRM API, MES API | Показывает конкуренцию за workers и приближение API к насыщению; полезнее количества пользовательских сессий для оценки нагрузки backend | `route` |
| Размер запросов и ответов (`http_request_size_bytes`, `http_response_size_bytes`) | Маршруты загрузки 3D-файлов Shop API, чтения файлов MES API и загрузки MES Dashboard | Помогает выявить слишком большие 3D-файлы и payload Dashboard, влияющие на сеть, память и latency | `route`, `direction` |

### Инфраструктура приложений и БД

| Метрика | Где собирается | Зачем нужна | Дополнительные labels |
|---|---|---|---|
| CPU utilization | Инстансы Shop API, CRM API и MES API | Показывает загрузку вычислительных ресурсов и помогает определить необходимость горизонтального масштабирования | `cpu` |
| Memory utilization | Инстансы Shop API, CRM API, MES API, Shop DB и MES DB | Позволяет обнаруживать нехватку памяти, утечки и риск OOM | `component` |
| Использование DB connection pool | Shop API, CRM API, MES API | Показывает количество активных, свободных и ожидающих соединений; ожидание соединения является признаком насыщения | `pool`, `state` |
| Количество соединений с БД | Shop DB, MES DB | Позволяет сравнивать текущие соединения с лимитом PostgreSQL и выявлять влияние общей Shop DB на Shop API и CRM API | `database`, `state` |
| Время выполнения запросов к БД | Shop DB, MES DB | Помогает найти медленные группы запросов и связать рост API latency с работой БД | `database`, `operation`, `query_group` |
| Блокировки и ожидающие транзакции | Shop DB, MES DB | Позволяет обнаружить конкуренцию за данные, в том числе между Shop API и CRM API в общей Shop DB | `database`, `lock_mode` |
| Размер БД и свободное место на диске | Shop DB, MES DB | Нужен для capacity planning и предупреждения остановки записи из-за заполнения диска | `database`, `volume` |
| Disk I/O utilization и I/O wait | Shop DB, MES DB | Показывает насыщение дисковой подсистемы, которое может увеличивать время выполнения запросов | `database`, `device` |
| Размер S3 и количество объектов | Хранилище 3D-файлов | Позволяет прогнозировать стоимость и рост хранилища, а также обнаруживать аномальное накопление файлов | `bucket`, `storage_class` |

### RabbitMQ

| Метрика | Зачем нужна | Labels |
|---|---|---|
| Количество сообщений в состоянии ready и in flight | Показывает, успевают ли consumers обрабатывать входящий поток; постоянный рост очереди является признаком насыщения | `environment`, `vhost`, `queue` |
| Возраст самого старого сообщения | Позволяет отличить кратковременный всплеск нагрузки от фактической задержки обработки заказа | `environment`, `vhost`, `queue` |
| Скорость публикации, доставки и подтверждения сообщений | Позволяет сравнить входящий и исходящий потоки и понять, на какой стороне возникает отставание | `environment`, `vhost`, `queue`, `operation` |
| Количество сообщений в DLQ/DLX | Показывает необработанные сообщения, которые могут означать потерянный или зависший этап заказа | `environment`, `vhost`, `queue` |
| Количество активных consumers | Помогает связать рост очереди с остановкой consumers или нехваткой экземпляров обработчика | `environment`, `vhost`, `queue` |

### Бизнес-метрики процесса заказа

| Метрика | Зачем нужна | Labels |
|---|---|---|
| Количество созданных заказов | Показывает фактический входящий поток и долю B2B/B2C-заказов | `environment`, `channel`, для ограниченного списка B2B-клиентов — `partner_id` |
| Количество заказов в каждом статусе | Показывает, на каком этапе накапливаются заказы | `environment`, `status`, `channel` |
| Количество переходов между статусами | Позволяет увидеть throughput каждого этапа и неуспешные переходы | `environment`, `from_status`, `to_status`, `channel`, `result` |
| Время нахождения заказа в статусе | Помогает определить этапы, из-за которых клиент ждёт дольше обещанных трёх недель | `environment`, `status`, `channel` |
| Количество заказов, превысивших допустимое время в статусе | Используется для alerts о зависших заказах до обращения клиента | `environment`, `status`, `channel` |
| Полное время обработки заказа | Показывает пользовательскую latency процесса от создания заказа до закрытия и позволяет контролировать выполнение обещанного срока | `environment`, `channel`, `result` |
| Время и результат расчёта стоимости | Позволяет наблюдать одну из самых длительных операций MES и оценивать влияние сложности модели на очередь | `environment`, `complexity_bucket`, `result` |

### Метрики, которые не выбираются в исходном виде

- RPS per user для Shop API и CRM API не собирается: `user_id` создаст высокую cardinality и не нужен для оценки состояния сервисов. Для управления B2B-нагрузкой используется ограниченный `partner_id`.
- Отдельные метрики количества HTTP 200 и HTTP 500 заменяются общим счётчиком запросов с label `status_code`.
- Количество пользовательских сессий не используется как основной показатель насыщения stateless API. Вместо него отслеживаются активные запросы, занятость workers и ожидание соединений с БД.
- Объём переданных данных не собирается для каждого API целиком на первом этапе. Размер запросов и ответов измеряется только для маршрутов 3D-файлов и MES Dashboard, где размер payload непосредственно влияет на производительность.

## План действий

1. Определить минимальный набор метрик для первого этапа внедрения.
2. DevOps-инженеру развернуть Prometheus и Grafana.
3. Подключить exporters для инфраструктуры, PostgreSQL и RabbitMQ.
4. Разработчикам внедрить API- и бизнес-метрики в Shop API, CRM API и MES API параллельно с развёртыванием инфраструктуры мониторинга.
5. Создать базовые dashboards и alerts для выбранного набора метрик.
6. Проверить интеграцию на dev-окружении и перенести конфигурацию в production.
7. Добавлять остальные метрики по результатам эксплуатации первого набора в рамках стандартного планирования и backlog команды.

# Архитектурное решение по логированию

## Системы и события для логирования

Централизованный сбор логов в первую очередь настраивается для Shop API, CRM API и MES API. Эти сервисы обрабатывают заказы, меняют их статусы, работают с RabbitMQ, базами данных и хранилищем 3D-моделей. Для пользовательских интерфейсов интернет-магазина, CRM и MES на первом этапе достаточно собирать необработанные ошибки JavaScript и ошибки критичных пользовательских действий. Обычные отладочные сообщения браузера централизованно собирать не нужно.

В приложениях используется структурированное логирование. В production логи формируются в JSON, а для локальной разработки может быть включён читаемый текстовый формат. Формат выбирается конфигурацией, но имена и смысл полей остаются одинаковыми.

Каждая запись должна содержать общий набор полей:

- время события в UTC и уровень логирования;
- имя, версию и окружение сервиса;
- стабильное имя события `event.name`;
- `trace_id` и `span_id`, если операция участвует в трассировке;
- идентификатор заказа `order.id` и идентификатор сообщения `message.id`, если они известны;
- канал поступления заказа B2C или B2B, псевдонимизированный `customer.id` и, при необходимости, псевдонимизированный идентификатор партнёра;
- результат операции, её длительность `duration_ms` и безопасный код ошибки.

Текст сообщения дополняет структурированные поля, но не заменяет их. Это позволяет искать события по заказу и трассе, строить агрегации и связывать логи с трейсами.

### События уровня INFO

| Система | Событие | Когда записывается | Дополнительные поля |
| --- | --- | --- | --- |
| Shop API | `order.created` | Создан новый заказ со статусом `INITIATED` | `order.id`, `customer.id`, канал, результат |
| Shop API | `model.upload.started` | Началась загрузка 3D-модели | `order.id`, тип и размер файла без имени и содержимого |
| Shop API | `model.upload.completed` | Файл сохранён, заказ переведён в `FILE_UPLOADED` | `order.id`, длительность, результат |
| Shop API | `price_calculation.requested` | Заказ переведён в `SUBMITTED` и отправлен на расчёт | `order.id`, `message.id`, результат |
| MES API | `price_calculation.started` | MES начал расчёт стоимости | `order.id`, источник B2B/B2C |
| MES API | `price_calculation.completed` | Расчёт завершён, статус изменён на `PRICE_CALCULATED` | `order.id`, длительность, результат без значения цены |
| CRM API | `manufacturing.approved` | Производство подтверждено, статус изменён на `MANUFACTURING_APPROVED` | `order.id`, результат |
| MES API | `order.status.changed` | Заказ перешёл в `MANUFACTURING_STARTED`, `MANUFACTURING_COMPLETED`, `PACKAGING` или `SHIPPED` | `order.id`, предыдущий и новый статусы, источник изменения |
| CRM API | `order.closed` | Заказ переведён в `CLOSED` | `order.id`, источник закрытия |
| Shop API, CRM API, MES API | `http.request.completed` | Завершился входящий HTTP-запрос | HTTP-метод, шаблон маршрута, статус ответа, длительность |
| Shop API, CRM API, MES API | `external.request.completed` | Завершился исходящий HTTP- или S3-запрос | система назначения, операция, статус, длительность |
| CRM API, MES API | `message.published` | Сообщение успешно опубликовано в RabbitMQ | очередь или routing key, `message.id`, `order.id` |
| CRM API, MES API | `message.received` | Consumer получил сообщение из RabbitMQ | очередь, `message.id`, `order.id`, номер доставки |
| CRM API, MES API | `message.processed` | Обработка сообщения успешно завершена | `message.id`, `order.id`, длительность |
| CRM API, MES API | `message.acked` | Consumer подтвердил RabbitMQ успешную обработку сообщения | очередь, `message.id`, `order.id` |
| Shop API, CRM API, MES API | `database.change.committed` | Зафиксировано значимое изменение заказа: создание, смена статуса, сохранение цены или производственного назначения | БД, тип операции, `order.id`, длительность |

Для HTTP-запросов логируется шаблон маршрута, например `/orders/{id}`, а не фактический URL с идентификатором. Тела запросов и ответов не записываются.

В INFO не входят отдельные SQL-запросы, операции чтения из БД и внутренние шаги алгоритма. Полный путь вызовов покрывается трейсингом, технические показатели — метриками, а в INFO остаются значимые бизнес-события и результаты операций. Для RabbitMQ дополнительно записываются публикация, получение, успешная обработка и подтверждение сообщения: это границы асинхронного процесса.

## Уровни логирования

- `DEBUG` — диагностические детали алгоритмов и промежуточных вычислений. В production уровень выключен по умолчанию и временно включается для конкретного сервиса или заказа на период расследования.
- `INFO` — штатные значимые бизнес-события, начало и успешное завершение обработки задачи, результаты внешних вызовов и фиксация важных изменений в БД.
- `WARN` — потенциально опасная ситуация, после которой операция продолжается: повторная попытка, fallback, повторная доставка сообщения, приближение к лимиту или медленный запрос.
- `ERROR` — текущая операция не выполнена: исчерпаны повторные попытки, сообщение отправлено в DLQ, невозможно сохранить статус, произошла ошибка SQL или недоступна зависимость.
- `FATAL` — сервис не может запуститься или продолжать работу, например из-за некорректной конфигурации или недоступности обязательного хранилища при старте.

Одна и та же ошибка не должна многократно записываться на каждом уровне стека. Компонент, который может обработать ошибку, добавляет контекст и использует `WARN`; компонент, на границе которого операция окончательно завершилась неуспешно, формирует `ERROR`.

## Мотивация

Сейчас ошибки и нестандартные ситуации разбирают преимущественно со слов клиента. Разработчикам и поддержке приходится вручную восстанавливать ход обработки заказа, что увеличивает длительность и стоимость расследования.

Трейсинг показывает цепочку вызовов конкретного запроса, а логи дополняют её сведениями о бизнес-событиях, результатах обработки и принятых приложением решениях. По `order.id`, `trace_id` и `message.id` поддержка сможет быстро найти историю конкретного обращения, а разработчики — определить место и причину сбоя, включая асинхронную обработку через RabbitMQ. Это снижает нагрузку на поддержку и инженеров, ускоряет восстановление сервиса и уменьшает потери от проблем с заказами.

Внедрение логирования должно повлиять на следующие метрики:

1. Снизить MTTR — среднее время восстановления после инцидента.
2. Снизить среднее время обработки обращения службой поддержки.
3. Снизить количество инженерных часов, затрачиваемых на расследование одного инцидента.
4. Увеличить долю инцидентов с установленной первопричиной.
5. После настройки алертов по логам снизить MTTD — среднее время обнаружения инцидента.

Сам по себе централизованный поиск по логам в первую очередь уменьшает MTTR. На MTTD решение начинает влиять после внедрения автоматических правил оповещения и обнаружения аномалий.

## Приоритет внедрения логирования и трейсинга

1. **MES API.** Выполняет расчёт стоимости, обрабатывает B2B-запросы и сообщения RabbitMQ, изменяет производственные статусы и работает с MES DB. Сервис находится в наиболее критичной части процесса и имеет больше всего предполагаемых точек деградации.
2. **Shop API.** Создаёт B2C-заказ, загружает 3D-модель и запускает цепочку расчёта. Инструментация позволит связать клиентское обращение с дальнейшей обработкой заказа.
3. **CRM API.** Участвует в ручном согласовании производства, публикует сообщения и получает из RabbitMQ созданные MES заказы B2B. Его подключение замкнёт сквозную наблюдаемость процессов B2C и B2B.
4. **Интеграции с RabbitMQ.** Наблюдаемость реализуется в producer и consumer перечисленных сервисов: фиксируются `message.id`, повторная доставка, подтверждение и попадание в DLQ. Отдельная доработка самого RabbitMQ для бизнес-логов не требуется.
5. **Frontend интернет-магазина, CRM и MES.** После серверных сервисов добавляется централизованный сбор необработанных JavaScript-ошибок и сбоев критичных действий. Полное логирование интерфейсов имеет меньший приоритет, потому что не показывает серверную первопричину и может создавать большой объём малоценных данных.

На каждом этапе логирование и трейсинг внедряются совместно: идентификаторы трассы автоматически добавляются в записи, а `order.id` и `message.id` передаются через синхронные и асинхронные границы.

## Предлагаемое решение

Обновлённая C4-диаграмма: [jewerly_c4_model_logging.drawio](jewerly_c4_model_logging.drawio).

Предлагаемый поток данных:

```text
Frontend errors -> logging endpoint соответствующего API
Shop API / CRM API / MES API -> JSON в stdout или локальный файл
    -> Fluent Bit
    -> Data Prepper
    -> OpenSearch
    -> OpenSearch Dashboards
```

- В Shop API, CRM API и MES API настраиваются стандартные библиотеки структурированного логирования и единая JSON-схема. Логи выводятся в `stdout` или локальный файл. Ротация локальных файлов используется как защита от заполнения диска и кратковременной недоступности центрального хранилища. Frontend отправляет только очищенные сообщения о необработанных ошибках в специальный endpoint соответствующего API; прямого доступа браузера к внутреннему контуру логирования нет.
- Fluent Bit устанавливается как агент на каждом узле или рядом с контейнерами приложений. Он читает локальные потоки, добавляет технические метаданные и передаёт записи дальше по защищённому соединению.
- Data Prepper принимает записи, проверяет и нормализует схему, маскирует запрещённые поля и маршрутизирует события по индексам.
- OpenSearch хранит и индексирует логи. На первом этапе можно использовать тот же кластер OpenSearch, который выбран для хранения трейсов, но создать отдельные индексы, политики жизненного цикла и квоты ресурсов для логов. При росте нагрузки логовое хранилище можно вынести в отдельный кластер.
- OpenSearch Dashboards предоставляет поиск, сохранённые запросы, дашборды и управление алертами. Поддержка ищет историю по `order.id`, а разработчики связывают записи с `trace_id`.
- `rsyslog` может остаться локальным транспортом и механизмом записи и ротации файлов, но не заменяет центральное индексируемое хранилище и интерфейс анализа.

## Политика безопасности

Система сбора и анализа логов размещается во внутреннем контуре. Доступ к OpenSearch Dashboards разрешён только через корпоративную сеть или VPN после аутентификации с SSO и MFA.

Используется ролевая модель:

- поддержка видит бизнес-события и выполняет поиск по идентификатору заказа, но не получает stack trace и внутренние технические поля;
- разработчики получают технические логи и stack trace, необходимые для диагностики;
- администраторы управляют индексами, сроками хранения, пользователями и правилами алертинга.

Передача между компонентами защищается TLS, для сервисных подключений используются отдельные учётные записи с минимальными правами. Данные в OpenSearch шифруются на диске, а обращения к логам и изменения настроек аудируются.

В логи запрещено записывать пароли, токены, cookie, платёжные данные, содержимое и имена 3D-файлов, тела HTTP-запросов и ответов, персональные данные клиента, полные SQL-запросы и их параметры. Идентификаторы клиентов и B2B-партнёров при необходимости псевдонимизируются. Фильтрация выполняется в приложении, а Data Prepper повторно удаляет или маскирует запрещённые поля перед сохранением.

## Политика хранения

Логи разделяются по системе и окружению, например:

- `logs-shop-api-prod`;
- `logs-crm-api-prod`;
- `logs-mes-api-prod`;
- `logs-frontend-prod`;
- `logs-infrastructure-prod`.

Отдельные индексы для каждого заказа, экземпляра приложения или уровня логирования не создаются. Это усложнит управление и приведёт к большому количеству мелких индексов.

Первоначальная политика хранения:

- rollover индекса выполняется раз в сутки или при достижении 20 ГБ;
- первые 30 дней логи доступны в быстром хранилище для поиска;
- с 31-го по 90-й день они перемещаются в более дешёвый слой или архив;
- после 90 дней автоматически удаляются;
- записи `ERROR`, относящиеся к подтверждённому инциденту, могут быть экспортированы в отдельный архив на срок расследования.

Через первый месяц эксплуатации необходимо измерить суточный объём, частоту обращений к старым данным и стоимость хранения, после чего скорректировать размер rollover и сроки. Локальные файлы ротируются по размеру и времени и хранятся только несколько дней, чтобы пережить временную недоступность центрального конвейера.

## Анализ логов, алертинг и поиск аномалий

В OpenSearch Dashboards создаются сохранённые запросы по `order.id`, `trace_id` и `message.id`, а также дашборды по количеству `WARN` и `ERROR`, HTTP 5xx, повторным попыткам, DLQ и переходам заказов между статусами.

На первом этапе настраиваются понятные пороговые алерты:

- появление сообщений в DLQ;
- резкий рост `ERROR` или HTTP 5xx;
- превышение числа повторных попыток и повторных доставок;
- наличие `price_calculation.started` без `price_calculation.completed` дольше установленного времени;
- серия неуспешных попыток аутентификации или отказов в доступе.

Алерты отправляются в рабочий канал команды и дежурному инженеру, а для критичных событий автоматически создаётся инцидент. У каждого правила должны быть владелец, уровень критичности, инструкция по первичной проверке и защита от повторяющихся уведомлений.

Поиск аномалий добавляется после накопления базового профиля нагрузки. Он должен выявлять нетипичные всплески B2B-запросов и создания заказов, изменение доли ошибок, рост повторных доставок и попыток входа. Обнаружение аномалий дополнит пороговые правила там, где фиксированный порог не учитывает суточный и недельный профиль нагрузки.

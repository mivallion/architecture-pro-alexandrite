# Архитектурное решение по трейсингу

## Покрытие и места возможного зависания заказа

Трейсинг охватывает Shop API, CRM API и MES API, а также их обращения к RabbitMQ, PostgreSQL и S3. На критическом пути возможны следующие отказы:

| Переход | Failure mode 1 | Failure mode 2 | Spans, отличающие ожидание от выполнения |
| --- | --- | --- | --- |
| Shop API → следующий этап обработки | Нет связи с CRM API или другим следующим сервисом | Следующий сервис вернул ошибку обработки | HTTP client span Shop API и server span принимающего сервиса; разрыв между ними показывает сетевое ожидание |
| Shop API → S3 | S3 недоступен | Загрузка файла завершилась по timeout | S3 client span с длительностью операции и статусом ответа |
| CRM API → RabbitMQ | RabbitMQ недоступен | Публикация не подтверждена или выполнена повторно | Producer span публикации с `message.id` и publisher confirm |
| RabbitMQ → MES API | Consumer остановлен | Handler завершился ошибкой, сообщение повторно доставлено или попало в DLQ | Разрыв между producer и consumer spans показывает ожидание в очереди; consumer span — время обработки |
| B2B-клиент → MES API | MES API или gateway недоступен | MES API вернул ошибку или timeout | Server span MES API и, при наличии, client span API Gateway |
| MES API → MES DB | БД или connection pool недоступны | SQL выполняется медленно из-за плана, блокировки или объёма данных | DB client span с временем ожидания соединения и выполнения запроса |
| MES API → S3 | S3 недоступен | Чтение 3D-модели выполняется слишком долго | S3 client span с операцией, размером объекта, длительностью и результатом |

Один заказ может обрабатываться в нескольких traces. Для их поиска используется общий `order.id`, а синхронные вызовы и сообщения RabbitMQ передают стандартный trace context.

## Данные, попадающие в tracing

Span содержит только данные, нужные для связи с заказом, определения компонента и результата операции. OpenTelemetry автоматически формирует trace- и span-контекст; бизнес-контекст и данные взаимодействия добавляются при инструментировании сервисов.

### Общие данные span

- `trace_id`, `span_id` и идентификатор родительского span;
- имя и тип операции (`span.name`, `span.kind`);
- время начала, время окончания и продолжительность операции;
- `service.name`, `service.version`, `deployment.environment.name` и идентификатор экземпляра;
- результат выполнения и статус span;
- `error.type` и exception event при ошибке;
- номер попытки retry, если операция выполнялась повторно.

### Бизнес-контекст заказа

- `order.id` — единый идентификатор заказа во всех связанных traces;
- канал создания заказа: B2B или B2C;
- предыдущий и новый статус заказа для операций перехода между статусами;
- результат перехода;
- fingerprint или криптографический hash `idempotency_key`, если операция поддерживает защиту от повторного выполнения; исходное значение ключа в tracing не сохраняется;
- обезличенный идентификатор партнёра для B2B-запросов, если он нужен для расследования.

`order.id` используется как attribute для поиска связанных traces, но не заменяет `trace_id`: отдельные этапы жизненного цикла одного заказа могут выполняться в разных traces.

### HTTP-вызовы

- HTTP method и шаблон route без фактических идентификаторов и query parameters;
- имя или адрес вызываемого сервиса;
- HTTP response status code;
- тип timeout или сетевой ошибки;
- номер повторной отправки запроса.

### RabbitMQ

- `messaging.system=rabbitmq`;
- имя exchange и queue;
- тип операции: `publish`, `process`, `ack` или `nack`;
- `messaging.message.id` и correlation/conversation ID;
- признак повторной доставки;
- результат публикации или обработки сообщения.

Producer должен передавать trace context в headers сообщения. Consumer создаёт новый span обработки и связывает его с producer span через переданный контекст. Временной разрыв между окончанием публикации и началом обработки показывает ожидание сообщения в очереди, а продолжительность consumer span — время непосредственной обработки.

### Вызовы PostgreSQL и S3

Для PostgreSQL записываются тип БД, имя БД, операция (`SELECT`, `INSERT`, `UPDATE`), имя таблицы или нормализованная группа запроса, время ожидания соединения и результат выполнения. Значения параметров SQL в tracing не передаются.

Для S3 записываются имя bucket, операция (`PUT` или `GET`), размер объекта, результат и тип ошибки. Имя файла и содержимое 3D-модели не передаются.

В tracing запрещено помещать тела HTTP-запросов и ответов, содержимое сообщений RabbitMQ и 3D-файлов, пароли, access tokens, персональные данные клиента и параметры SQL с пользовательскими данными.

## Мотивация

Сейчас при зависании или потере заказа разработчики и специалисты поддержки не могут восстановить фактическую цепочку его обработки по Shop API, CRM API, RabbitMQ, MES API, PostgreSQL и S3. Расследование начинается со слов клиента и требует ручного сопоставления данных нескольких систем. Это увеличивает продолжительность и совокупную стоимость работы с дефектами.

Distributed tracing позволит по `order.id` найти связанные технические операции, увидеть продолжительность каждого вызова и ожидание между вызовами, обнаружить retry и повторную доставку сообщения, а также определить компонент и операцию, на которых цепочка завершилась ошибкой. Линия поддержки сможет быстрее передать разработчикам технический контекст обращения, не запрашивая у клиента внутренний `trace_id`.

Эффект внедрения измеряется по следующим показателям:

1. **Mean Time to Repair (MTTR)** — среднее время от обнаружения инцидента до восстановления работы.
2. **Среднее время локализации неисправного компонента** — время от начала расследования до определения конкретного сервиса или интеграции, где возникла проблема.
3. **Среднее время обработки обращения о зависшем заказе** службой поддержки.
4. **Трудозатраты технических специалистов на одно расследование**, измеряемые в человеко-часах.
5. **Доля заказов с восстанавливаемой цепочкой операций** — процент заказов, для которых по `order.id` находятся связанные spans всех инструментированных этапов.

Базовый tracing работает реактивно и сам по себе не уменьшает Mean Time to Detect (MTTD): команда начинает поиск после сигнала мониторинга или обращения пользователя. MTTD может снизиться только при дополнительном автоматическом анализе traces, который обнаруживает оборванные цепочки, превышение допустимой продолжительности и чрезмерное количество retry и создаёт alerts.

## Предлагаемое решение

Shop API, CRM API и MES API инструментируются через OpenTelemetry SDK и auto-instrumentation. Сервисы создают HTTP, messaging, PostgreSQL и S3 spans, добавляют бизнес-контекст заказа и передают W3C Trace Context в HTTP-заголовках и headers сообщений RabbitMQ. По OTLP завершённые spans поступают в OpenTelemetry Collector, где проходят batch-обработку и фильтрацию чувствительных attributes, затем экспортируются в Jaeger Backend. OpenSearch хранит данные, а сотрудники поддержки и разработчики ищут связанные traces по `order.id` в Jaeger UI.

## Компромиссы

- Трейсинг не восстанавливает события, произошедшие до инструментирования, и не показывает ручные действия вне системы. Для уже зависших заказов по-прежнему могут потребоваться логи и данные из БД.
- Один trace не должен жить весь многодневный жизненный цикл заказа. Отдельные синхронные и асинхронные этапы образуют разные traces, которые связываются через `order.id` и `message.id`; поэтому полнота расследования зависит от корректной передачи этих идентификаторов.
- Полное сохранение всех spans увеличивает сетевые расходы и объём OpenSearch. На первом этапе ошибки и редкие критичные операции сохраняются полностью, а для успешных массовых запросов может применяться sampling. Sampling уменьшает стоимость, но может исключить часть нормальных цепочек из последующего анализа.
- Трейсинг добавляет небольшие расходы CPU, памяти и сети. Collector с batch-обработкой ограничивает влияние на приложения, а недоступность tracing-контура не должна останавливать обработку заказов: spans временно буферизуются в допустимых пределах или отбрасываются с отдельной метрикой потерь.
- Автоинструментация хорошо покрывает HTTP, PostgreSQL и RabbitMQ, но не объясняет внутренние бизнес-решения. Для переходов статуса, расчёта стоимости и повторных попыток потребуются ручные spans и attributes, что увеличивает объём разработки и сопровождения.
- Frontend и внешние системы партнёров на первом этапе не покрываются полностью. Цепочка начинается на входе Shop API, CRM API или MES API; диагностика действий внутри браузера и инфраструктуры партнёра потребует отдельной инструментации и может оказаться несоразмерно дорогой.
- Трейсинг ускоряет расследование конкретной цепочки, но не заменяет метрики, alerts и логи. Без внешнего сигнала о проблеме базовое решение уменьшает MTTR, но не MTTD.

## Безопасность

Компоненты tracing размещаются во внутреннем контуре без публичных IP. Доступ к Jaeger UI разрешён из внутренней сети или через корпоративный VPN после аутентификации в корпоративном Identity Provider с MFA.

Доступ разграничивается с помощью Role-Based Access Control по принципу least privilege:

- роль `support` может только искать и просматривать traces по `order.id`;
- роль `developer` может просматривать технические attributes, ошибки и stack traces;
- роль `admin` управляет конфигурацией Jaeger, Collector, sampling, retention и доступом пользователей.

Shop API, CRM API и MES API отправляют spans в Collector с использованием отдельных service accounts. OTLP и остальные внутренние соединения защищаются TLS, а для аутентификации сервисных клиентов при необходимости используется mTLS. OpenSearch доступен по сети только Jaeger Backend; пользователи и инструментированные сервисы не подключаются к нему напрямую. Исходящие соединения Collector ограничиваются разрешёнными внутренними адресами Jaeger Backend.

Ограничения на состав spans, перечисленные выше, применяются в SDK. Перед сохранением traces Collector повторно фильтрует и удаляет запрещённые attributes. Данные в OpenSearch шифруются at rest, а секреты подключения хранятся в корпоративном secret storage, а не в конфигурационных файлах.

Входы пользователей, поисковые запросы к tracing-системе и административные изменения записываются в audit log для расследования несанкционированного или избыточного доступа.

Для traces настраивается ограниченный срок хранения: 30 дней в быстром поисковом слое и автоматическое удаление не позднее 90 дней, если trace не сохранён отдельно как материал подтверждённого инцидента. Срок пересматривается после оценки объёма и фактической глубины расследований.

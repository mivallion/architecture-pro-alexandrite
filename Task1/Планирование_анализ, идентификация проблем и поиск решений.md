# Планирование: анализ, идентификация проблем и поиск решений

## Существующие проблемные места
- Система не справляется с ростом количества заказов: покупатели ждут несколько месяцев вместо обещанных трёх недель, хотя производство укладывается в срок
  - Нет данных, на каком этапе задерживаются заказы: мониторинг переходов между статусами не описан
    - Одна из гипотез — задержки связаны с медленной главной страницей MES и работой операторов
  - После подключения заказов других продавцов через API обработка замедлилась ещё сильнее
- Каждое приложение работает в одном экземпляре; для MES с расчётами длительностью от двух минут до получаса это ограничивает пропускную способность
- Главная страница MES долго загружается и мешает работе операторов
- QA-инженер вручную запускает E2E-тесты, поэтому обратная связь о регрессиях приходит поздно, а найденные ошибки задерживают релизы. Критические E2E-сценарии следует автоматически запускать в CI, например после развёртывания develop-окружения и по расписанию
- MES Dashboard работает медленно даже с пагинацией и фильтрацией; нужно проверить запросы и индексы MES DB
- B2B-пользователи обращаются к MES API напрямую, поэтому границы внешнего взаимодействия и ограничения нагрузки не контролируются единым API Gateway
- CRM API и Shop API используют общую Shop DB — антипаттерн shared database
  - Два независимых bounded context конкурируют за соединения, блокировки строк и ввод-вывод одной БД
  - Рост нагрузки одного приложения может ухудшить производительность другого, но по C4-схеме эта БД не связана напрямую с MES Dashboard, который работает через MES API и MES DB
  - Нет изоляции данных — изменение схемы одним сервисом может сломать другой
- 3D-файлы загружаются в S3 через Shop API, MES API их оттуда читает — но на схеме нет механизма нотификации о том, что новый файл готов к расчёту
  - Если MES polling'ит S3 или полагается на shared DB, это создаёт лишнюю задержку и нагрузку

## Потенциальные проблемные места
- Базы данных работают в одном экземпляре, что ограничивает отказоустойчивость; необходимость репликации и шардирования следует оценивать по нагрузке и требованиям к доступности
- Поддержкой приложения занимается продакт-менеджер; при росте бизнеса может понадобиться отдельная линия поддержки B2C, чтобы он сосредоточился на работе с бизнесом и развитии продукта
- Ручной деплой на release- и prod-окружения повышает риск ошибок
- MES продаётся бизнес-клиентам, но его развивает один C#-разработчик; при росте нагрузки на команду потребуется обучить Java-разработчиков или расширить C#-команду
- Конфигурация RabbitMQ не описана. Нужно проверить глубину очередей, DLQ, retry-политики и пределы пропускной способности
- На C4-схеме нет прямого HTTP-соединения между Shop API и MES API — непонятно, как заказ физически передаётся из магазина в MES
  - Если через общую Shop DB, то существует не отражённая на схеме связь MES API с этой БД и скрытая зависимость процесса передачи заказа от её схемы и нагрузки
  - Если через RabbitMQ — на схеме это не отображено, что говорит о пробелах в документировании архитектуры

## Инициативы
- Внедрить базовый мониторинг на основе Prometheus и Grafana
  - Собирать бизнес-метрики: количество новых B2C-заказов и поступающих задач, переходы между статусами, время нахождения заказа в каждом статусе
  - Собирать технические метрики критического пути заказа: время выполнения и статусы ответов Shop API, CRM API и MES API, глубину и возраст сообщений RabbitMQ, загрузку приложений и БД
  - Построить отдельные дашборды для бизнес- и технических метрик, настроить оповещения о превышении согласованных порогов
- Провести time-boxed диагностику производительности MES Dashboard
  - В течение одной недели исследовать цепочку загрузки от браузерного запроса до MES API и MES DB: измерить длительность этапов, количество и время SQL-запросов, проверить планы выполнения, индексы, блокировки и объём возвращаемых данных
  - По итогам определить подтверждённые узкие места и отдельно оценить инициативы по их устранению
- Внедрить готовый API Gateway с rate limiting для внешнего API
  - Направить через gateway все B2B-запросы, идентифицировать партнёров, настроить общие и индивидуальные квоты и ответы `429 Too Many Requests`
  - Проверить ограничения нагрузочными тестами и согласовать условия использования API с партнёрами
- Внедрить репликацию БД
  - Настроить запросы, для которых это допустимо, на чтение с реплики
- Внедрить горизонтальное конфигурируемое масштабирование MES
- Кэширование запросов, в первую очередь MES API
- Внедрить автоматический запуск тестов E2E на develop окружении
- Нанять второго C#-разработчика, чтобы снизить bus factor
- Вынести расчет стоимости в отдельный сервис
- Разделить БД онлайн-магазина и CRM
  - CRM должна иметь собственную БД, интеграция — только через RabbitMQ (API → queue → CRM)
  - Это устранит антипаттерн shared database и снизит конкуренцию за ресурсы БД
- Внедрить event-driven нотификацию о загрузке 3D-моделей
  - После загрузки файла в S3 отправлять событие в RabbitMQ, чтобы MES начинала расчёт, а не полагалась на polling или shared DB

## Приоритеты инициатив
Приоритет учитывает риск потери клиентов и контрактов, трудоёмкость и зависимости между инициативами. Сначала идут небольшие изменения, которые сдерживают деградацию и дают данные для более дорогих архитектурных решений. Часть инициатив можно выполнять параллельно: следующая работа не обязана ждать полного завершения предыдущей.

Полный порядок инициатив:

| Приоритет | Инициатива | Обоснование порядка |
| --- | --- | --- |
| 1 | Базовый мониторинг | Уменьшает неопределённость и предоставляет данные для всех последующих решений |
| 2 | API Gateway с rate limiting | Быстро ограничивает неконтролируемую нагрузку, появившуюся после открытия B2B API |
| 3 | Time-boxed диагностика MES Dashboard | Локализует узкое место без преждевременной дорогой оптимизации |
| 4 | Кеширование листинга MES | Может быстро снизить нагрузку на MES DB, но внедряется после подтверждения профиля чтений и правил актуальности |
| 5 | Горизонтальное масштабирование MES | Увеличивает пропускную способность после устранения ограничений stateful-обработки и проверки результата нагрузочными тестами |
| 6 | Автоматический запуск E2E-тестов | Сокращает задержки релизов и риск регрессий, но не устраняет текущую деградацию напрямую |
| 7 | Event-driven нотификация о загрузке 3D-моделей | Устраняет скрытый polling и делает передачу заказа явной после уточнения существующего процесса |
| 8 | Наём второго C#-разработчика | Снижает зависимость от одного специалиста и ускоряет изменения MES; наём можно начинать параллельно, но эффект проявится не сразу |
| 9 | Выделение расчёта стоимости в отдельный сервис | Позволяет независимо масштабировать долгую операцию, но требует подтверждения, что именно расчёт ограничивает систему |
| 10 | Репликация БД | Повышает доступность и разгружает допустимые чтения, но не поможет запросам, которым необходимы самые актуальные данные, без дополнительной схемы маршрутизации |
| 11 | Разделение Shop DB и CRM DB | Устраняет стратегический антипаттерн shared database, но является дорогой миграцией и не имеет подтверждённой прямой связи с текущей задержкой MES Dashboard |

### 1. Внедрить базовый мониторинг
- **Почему сейчас:** причина многомесячных задержек заказов не установлена; без метрик есть только предположения, поэтому нельзя обоснованно выбирать дорогие оптимизации
- **Конкретный объём:** ввести в эксплуатацию Prometheus и Grafana, собрать ограниченный набор бизнес- и технических метрик критического пути заказа, построить дашборды и настроить оповещения
- **Измеримый результат:** команда видит, на каком статусе накапливаются заказы, задержки и долю ошибок критических API; отклонения обнаруживаются по оповещениям, а не по жалобам клиентов
- **Effort:** 2/5 — базовая инструментализация и развёртывание являются типовыми задачами; оценка относится к ограниченному MVP, а не к полному покрытию всех компонентов

### 2. Внедрить API Gateway с rate limiting
- **Почему сейчас:** работа системы ухудшилась после открытия прямого доступа партнёров к MES API; ограничение внешней нагрузки — быстрое защитное действие, не требующее считать эту корреляцию доказанной причиной
- **Конкретный объём:** выбрать готовый API Gateway, направить через него весь B2B-трафик, настроить идентификацию партнёров, общие и индивидуальные квоты, ответы `429`, нагрузочные тесты и уведомление партнёров
- **Измеримый результат:** весь B2B-трафик проходит только через gateway, нагрузочный тест подтверждает соблюдение квот, а один партнёр не может занять все доступные ресурсы MES API
- **Effort:** 3/5 — используются готовые инструменты, но необходимы переключение трафика, тестирование и согласование условий с партнёрами

### 3. Провести time-boxed диагностику MES Dashboard
- **Почему сейчас:** медленный Dashboard уже мешает работе операторов, но конкретная причина задержки неизвестна, поэтому полная оптимизация имеет неопределённый объём и может оказаться дорогой
- **Конкретный объём:** за одну неделю исследовать цепочку от браузера до MES DB и измерить длительность её этапов; диагностика может идти параллельно с внедрением постоянного мониторинга с помощью доступных логов, браузерных замеров, SQL-статистики и `EXPLAIN ANALYZE`
- **Измеримый результат:** определены операции, формирующие основную часть времени загрузки; для них зафиксированы измеренная длительность, подтверждённая причина и предварительная оценка исправления
- **Effort:** 2/5 — одна неделя работы одного разработчика; исправление найденных узких мест оценивается отдельно

Эти три инициативы первыми ограничивают внешнюю нагрузку, уменьшают неопределённость и позволяют перейти к адресному исправлению подтверждённого узкого места. Остальные требуют больше времени либо пока не имеют подтверждённой связи с потерей клиентов и контрактов.

## Целевая архитектура через полгода

Целевая архитектура развивается эволюционно на основании измерений, а не через одновременную замену всех компонентов.

- Весь внешний B2B-трафик проходит через API Gateway. Партнёр аутентифицируется, для него применяются общие и индивидуальные rate limits, а MES API больше не доступен партнёрам напрямую.
- Shop API, CRM API, MES API, RabbitMQ, PostgreSQL и инфраструктура покрыты базовым мониторингом. В Grafana разделены технические и бизнес-дашборды, настроены оповещения по ошибкам, перегрузке, очередям и зависшим статусам заказа.
- Для критического пути заказа внедрены единые `order.id`, trace context и структурированные логи, благодаря чему запрос поддержки можно связать с метриками, трассой и событиями обработки.
- Подтверждённые диагностикой узкие места MES устранены адресно. Для листинга Dashboard оптимизированы запросы и, если профиль нагрузки подтверждает пользу, используется серверный кеш; длительные операции MES могут масштабироваться отдельно от пользовательских запросов.
- MES API подготовлен к горизонтальному масштабированию: состояние заказа хранится вне экземпляра приложения, повторные сообщения обрабатываются идемпотентно, а пропускная способность проверяется нагрузочными тестами. Количество экземпляров определяется измеренной нагрузкой, а не предположением.
- RabbitMQ имеет контролируемые retry, DLQ и метрики возраста очереди. Передача заказов и 3D-моделей между системами описана явно и не зависит от недокументированного polling.
- Для Shop DB и CRM DB определён план устранения shared database. Полная миграция может выходить за горизонт шести месяцев, но новые интеграции уже не должны усиливать совместное владение схемой.

Через полгода архитектура должна выдерживать текущую нагрузку и давать команде измеримые основания для масштабирования и приёма новых B2B-клиентов.

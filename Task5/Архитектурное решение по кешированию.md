# Архитектурное решение по кешированию

## Мотивация

Операторы жалуются на низкую скорость MES Dashboard. При открытии и обновлении страницы MES API многократно выполняет похожие запросы на получение списка заказов из MES DB. Такие запросы могут включать фильтрацию, сортировку и пагинацию, создают дополнительную нагрузку на PostgreSQL и увеличивают время ответа интерфейса.

Предлагается кешировать результаты серверных запросов на получение списка заказов для MES Dashboard. Это должно:

- уменьшить время ответа листинговых методов MES API;
- сократить количество тяжёлых запросов к MES DB и освободить её ресурсы для расчётов и изменения заказов;
- повысить скорость работы операторов с MES Dashboard.

В кеш включаются только представления списка заказов: набор полей, необходимых дашборду, с учётом фильтров, сортировки, страницы и области доступа пользователя. Изменение статуса, расчёт стоимости и другие команды не кешируются. MES DB остаётся единственным источником истины.

Кеширование не заменяет диагностику запросов и оптимизацию схемы MES DB. Перед внедрением и после него необходимо измерять длительность запросов, частоту одинаковых чтений и соотношение чтений и изменений. Предположение о частых чтениях и относительно редких изменениях должно быть подтверждено мониторингом.

## Предлагаемое решение

Диаграмма последовательности чтения списка и изменения статуса: [mes_orders_cache_sequence.puml](mes_orders_cache_sequence.puml).

### Серверное кеширование

Между MES API и MES DB добавляется Redis. Кеширование реализуется на стороне MES API, потому что серверный кеш:

- переиспользуется всеми экземплярами MES API и пользователями с одинаковой областью доступа;
- централизованно инвалидируется при изменении заказа;
- не зависит от состояния браузера и не позволяет клиенту определять срок актуальности данных.

Клиентское кеширование для списка заказов не подходит: разные операторы могут видеть разные наборы данных, браузер не знает об изменениях, выполненных другими пользователями, а принудительно инвалидировать данные во всех открытых клиентах сложнее.

Redis не является прозрачным прокси и не обращается к MES DB самостоятельно. MES API управляет чтением и записью кеша, а при недоступности Redis выполняет запрос непосредственно к MES DB.

### Паттерн Cache-Aside

Для листинга используется паттерн Cache-Aside:

1. MES API получает из MES DB текущую версию списков заказов.
2. На основе версии и параметров запроса формируется ключ Redis.
3. MES API пытается получить список из Redis.
4. При попадании значение возвращается клиенту без выполнения тяжёлого запроса листинга к MES DB.
5. При промахе MES API читает актуальный список из MES DB, сохраняет результат в Redis и возвращает его клиенту.
6. Если Redis недоступен, MES API пропускает кеш и читает данные из MES DB.

Чтение небольшого счётчика версии не устраняет все обращения к MES DB, но заменяет тяжёлый листинговый запрос дешёвым обращением по первичному ключу и обеспечивает требуемую актуальность после изменения заказа.

Пример ключа:

```text
mes:orders:list:v{version}:{access-scope}:{filters-hash}:{sort}:{page}
```

В значение записывается сериализованный DTO списка, а не сущности базы данных. В ключ обязательно включается область доступа, чтобы пользователь не получил результат, сформированный для другой роли или производственного участка. `access-scope` вычисляется MES API из проверенного authorization context и приводится к каноническому значению; клиент не может передать готовый scope или ключ кеша.

Cache-Aside выбран потому, что в Redis попадают только востребованные варианты листинга, а не все возможные сочетания параметров.

Другие паттерны подходят хуже:

- **Write-Through** потребовал бы при каждом изменении заказа синхронно обновлять все варианты списков, в которые он мог попасть. Один заказ может присутствовать на разных страницах и в выборках с разными фильтрами, поэтому пересчитать их все сложно. Кроме того, доступность операции записи стала бы зависеть от Redis.
- **Refresh-Ahead** периодически обновляет кеш до истечения TTL, но между обновлениями может возвращать устаревший статус. Он также создаёт фоновые запросы для списков, которые могут больше не использоваться.

### Стратегия инвалидации

Основная стратегия — программная версионированная инвалидация. В MES DB добавляется счётчик версии листинга заказов, например запись `orders_list` в таблице `cache_versions`.

Изменение статуса заказа и увеличение версии выполняются в одной транзакции MES DB:

```text
UPDATE orders SET status = ...;
UPDATE cache_versions SET version = version + 1 WHERE cache_name = 'orders_list';
COMMIT;
```

После успешного commit следующий запрос получает новую версию и формирует новый ключ Redis. Старые списки остаются физически в Redis, но больше не читаются и удаляются после истечения TTL. Если транзакция откатывается, версия не изменяется и существующий кеш остаётся корректным.

На первом этапе используется один общий счётчик: создание заказа, изменение статуса, назначение оператора или другое изменение, влияющее на листинг, инвалидирует все варианты списка. Все изменения MES DB должны проходить через единый write path MES API: это относится к действиям Dashboard, прямым B2B-командам и сообщениям RabbitMQ от CRM. Обработчик каждой такой команды изменяет заказ и версию в одной транзакции. Это грубая, но простая и надёжная стратегия. Если измерения покажут слишком низкий cache hit ratio, счётчики можно разделить по производственному участку или другому устойчивому признаку.

TTL устанавливается как страховочный механизм очистки, а не как основной способ обеспечения актуальности. Начальное значение — 5 минут с небольшим случайным отклонением, чтобы много ключей не истекали одновременно. Конкретное значение корректируется после измерения объёма Redis, частоты изменений и повторного использования списков.

Только временная инвалидация не подходит, потому что до истечения TTL может возвращаться старый статус. Удаление отдельных ключей без версии также неудобно: при изменении одного заказа трудно определить все страницы и фильтрованные списки, в которых он присутствует.

### Обработка конкурентных запросов и отказов

После успешного commit последующие запросы используют ключ новой версии и не обращаются к прежнему кешу. Запрос, начавшийся до завершения транзакции, ещё может получить предыдущее состояние; это соответствует порядку выполнения конкурентных операций.

При недоступности Redis MES API переходит на чтение из MES DB. Ошибка кеша логируется и учитывается в метриках, но не превращается в недоступность MES. Для защиты от cache stampede при одновременном промахе большого количества запросов следует использовать короткую распределённую блокировку или single-flight на один ключ; остальные запросы ожидают первый результат либо читают MES DB с ограничением параллелизма.

### Контроль результата

После внедрения необходимо контролировать:

- p95 и p99 времени ответа метода получения списка заказов;
- cache hit ratio Redis;
- количество и длительность запросов листинга к MES DB;
- загрузку CPU и число активных соединений MES DB;
- ошибки и время ответа Redis;
- случаи возврата списка, версия которого не соответствует текущей версии в MES DB.
